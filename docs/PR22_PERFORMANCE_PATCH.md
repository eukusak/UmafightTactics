# PR22: Render 성능 개선과 설명 가독성

## 변경 범위

| 영역 | 변경 | 목적 |
|---|---|---|
| Render / server/index.ts | 새 CDN 정적 사이트 + 멀티플레이 전용 서버 | 이미지·음악·HTTP gzip과 경기 계산 분리 |
| origins / endpoint | 명시적 wss URL, 정확한 Origin 허용 목록, 45초 첫 연결 대기 UI | 다른 도메인 프런트와 재접속 지원 |
| rooms / protocol / onlineStore | 50ms 게임 시계 유지, 100ms 프레임 묶음, 회전초밥 draft 증분, 변경된 AI 배치만 전체 상태 알림 | 동일 판정으로 반복 직렬화·전송 감소 |
| backpressure | 커서 보존, 64프레임 이력 묶음, 지속 정체 시 재접속 | 느린 수신자 때문에 무한 전송 큐가 생기는 현상 완화 |
| App / Vite | 전투·도감·모션·온라인 지연 로딩, 공통 CJS helper 분리, 로딩/복구 안내 | 제목에서 Phaser 다운로드·평가 방지 |
| 도감 | viewport 이미지 lazy loading | 145명 초상화를 동시에 요청하지 않음 |
| 오디오 / build | 원본 보존, 배포 BGM 160kbps, 원본 해시 인코딩 캐시, 빌드 버전 URL, 개발 진단 | CDN 전송량과 반복 빌드 작업 감소 |
| 글꼴 / 설명 | 둥근 Jua 제목·라벨, Noto 설명, 문장별 블록·줄간격·한국어 줄바꿈 | 귀여운 게임 인상과 긴 설명 가독성 |
| 증강 설명 | 공통 보너스는 스킬 설명에서 제외, 전용 기물 스킬 업그레이드 및 지정 아이템 효과만 표시 | 기물 기본 스킬과 공통 증강 혼동 방지 |

공통 증강의 전투 효과는 삭제하지 않았다. 공통 증강은 기존 증강 상세 패널에서 확인한다. 성급별 수치 표, 전용 영구 성장 기록, 아이템 중첩 보존과 소유자 구분은 유지한다.

## 측정

기존 빌드의 실제 초기 JS 목록과 새 Vite manifest의 정적 의존성 그래프를 비교했다. 글꼴·이미지·음악은 아래 JS 합계에 포함하지 않는다. JSON 원자료는 performance/pr22-bundle.json이다.

| 초기 JS | 이전 | 변경 후 |
|---|---:|---:|
| 원본 UTF-8 bytes | 2,323,872 | 647,602 |
| gzip bytes | 558,871 | 165,663 |

초기 JS gzip 합계는 약 70.4% 감소했다. 전체 게임 데이터까지 모두 지연 로딩한 것은 아니며 gameStore가 공유하는 규칙·로스터 데이터는 초기 그래프에 남는다. 큰 Phaser 청크는 전투/모션 진입 시 요청한다. 500KB 경고 한도를 올리지 않았다.

24곡(제목곡+23곡)의 소스는 189~200kbps였다. 배포 음악 합계 139,728,836 → 114,822,840 bytes(약 17.8% 감소). MP3 메타데이터 검사에서 24곡 모두 160kbps이며 원본과 재생시간 차이는 0초다. 손실 재인코딩이므로 원본을 public/assets/audio에 보존하고, 바이트가 동일했던 루트 중복본 26개만 제거했다. 전곡 사전 로딩은 하지 않고 현재 Audio 객체 하나를 사용한다. 객관적 청감 동등성을 주장하지 않는다.

|---|---:|---:|---:|---:|---:|
| 1 × 2 | 177.9 | 21.5 | 936.5 | 29707 | 0 |
| 1 × 8 | 157.4 | 24 | 722.9 | 126952 | 0 |
| 2 × 8 | 229.8 | 33.8 | 1195.4 | 230307 | 0 |

각 8초, 실제 WebSocket과 7레벨 AI 편성 사용. CPU는 서버와 부하 클라이언트가 같은 Node 프로세스에서 사용한 합계이며 단일 코어 기준이다. 브라우저 회귀 검사도 실행 중이었던 개발 PC 결과다. 첫 전투 계산을 포함한 최대 지연이며 평상시 50ms tick의 SLA가 아니다. 압축 후 수신 bytes/s는 테스트 클라이언트의 실제 TCP data로 계측했다. 원자료: performance/pr22-load.json.

## 검증

- npm ci, production-only npm ci --omit=dev 설치 및 dist/public/Vite/FFmpeg 없는 서버 기동 성공.
- 전체 단위 테스트 573개 통과. 이후 전용 증강 표시 변경 6개 및 최종 WebSocket/프레임 전송 7개 회귀 검증 통과.
- 타입 검사, lint, Vite + 음악 빌드, 초기 번들 경계 검사 통과.
- 운영 시작 경로 10개: 직접/래퍼/정적/로컬, 심볼릭 링크, 잘못된 PORT, import 부작용, HTTP 정적 분리, MP3 Range 206.
- 데이터 145명·5시즌, 엄격 아트 514/514 확인.
- 공식 Render draft2020-12 JSON Schema 검증 통과.
- 브라우저 120개(PC/노트북 및 모바일 시나리오)는 실행 중이며 최종 결과를 이 문서에 갱신한다.

새 네트워크 정책에 맞춰 기존 테스트도 수정했다. 초상화 145장은 도감을 끝까지 스크롤한 뒤 모두 디코딩되는지 확인하고, 오디오 재생 검증은 캐시 버전 query를 제외한 pathname을 비교한다. 테스트 범위를 삭제하지 않았다.

## 운영 조건과 한계

**병합 전에 기존 Render 서비스 자동 배포를 중지하고 [분리 배포 가이드](RENDER_SPLIT_DEPLOYMENT.md)를 따른다.** 기존 서비스에서 새 npm start를 바로 실행하면 HTML 대신 서버 상태만 제공한다. 프런트 VITE_MULTIPLAYER_URL 및 서버 ALLOWED_ORIGINS를 실제 두 서비스 URL에 맞춘 후 전환한다. 이번 PR에서 운영 서비스 생성·유료 플랜 변경·병합은 수행하지 않는다.

실측은 Windows 개발 PC의 짧은 부하 시험이며 Render의 CPU/메모리 용량 또는 WAN 지연 보장이 아니다. 기존 동기식 라운드 계산은 여전히 여러 방이 동시에 시작할 때 긴 tick drift를 만든다. 1배속·최대 8인·서버 판정·보상·재접속을 보존했으며, worker thread나 별도 simulation worker는 다음 단계 후보다. 공식 문서와 수동 배포 체크 항목은 분리 배포 가이드에 있다.
